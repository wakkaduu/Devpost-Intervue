Intervue: app map

A mock interview web app. You pick a track, answer questions by voice or in writing, and the AI reviews each answer, quoting what you actually said. This page shows where the main pieces live, so you know where to look when you want to change something. It works offline and needs no script.

The few main pieces

Screens (browser)

app/ holds the pages (Home, interview, results, history, login). components/ holds the pieces they are built from.

Server doors (API routes)

app/api/ is where the browser asks the server for things: review, review/summary, transcribe, speak, history, and auth/*. Secret keys live only here.

Logic and services

lib/ holds the review prompts and the Gemini, Groq and basic graders, scoring, history, autosave, validation, rate limiting, email and the server voice.

Data

data/questions.json (52 tracks of 15 questions), the browser's localStorage for guests, and Supabase (supabase/schema.sql) for accounts and saved sessions.

One action, end to end: answering a question

A route to follow (reference route)

This is a suggested way to read the code for the action above. It was not toured step by step; use it when you want to trace how an answer turns into a review.

Stop 1 The browser asks for a review

context/SessionContext.tsx → search for const runReview. It builds the request (question, answer, mode, earlier feedback points so the AI doesn't repeat itself), calls /api/review in the background, and stores the result on the answer.

Stop 2 The server door checks and delegates

app/api/review/route.ts → export async function POST. It applies the rate limit, reads the body safely, validates it with validateReviewRequest (lib/validation.ts), then calls evaluateAnswer. Errors are turned into a generic message so internals never reach the user.

Stop 3 The provider chain

lib/evaluator.ts → export async function evaluateAnswer. Gemini first, then Groq, each with its own time limit, then basicReview. The response says which one answered (source and provider), and the prompt that asks for feedback quoting the person's own words is buildPrompt in lib/gemini.ts.

A practice to reuse

Turn a reported bug into a failing test before fixing it

What happened: voice recording needed two clicks in Brave. The report said the error “flashed” and the second click worked. That clue pointed to the order of events: Brave opens the microphone and only then reports that live captions failed, which the fallback code did not expect.

The evidence: the tests in components/__tests__/AudioFallback.test.tsx under “the Brave case” recreate exactly that order. They failed on the old components/VoiceAnswer.tsx and pass on the fix (see const switching), so the bug can't quietly come back.

Use it again: on any project, write down the exact symptom and the sequence behind it, reproduce it as a test that fails, then change the code until it passes. A fix with a failing-then-passing test is much easier to trust than one that “looks right”.
